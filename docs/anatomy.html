What a feed handler actually does

It is a translator with a memory. Bytes arrive off a wire; a current picture of the market comes out. Everything below is that one sentence, drawn at four levels of detail.

01 — THE LOGICFive operations, and only five

Bytes in on the left, best bid and offer out on the right. The first three operations are pure byte shuffling: no memory, just counters and wires. The last two hold state, and that is where all the difficulty lives.

02 — SOFTWARE vs HARDWAREThe same five operations, twice

Left is what the Python model in model/ does. Right is what the SystemVerilog has to do instead. The middle column is the interesting part: what you give up in the translation.

The one property that matters most. max(self.bids) walks every live price level, so its cost depends on what the book looks like. A market data feed cannot be told to slow down — there is no flow control, and a dropped message means a permanently wrong book. Variable latency is therefore not merely undesirable, it is disqualifying.

The bitmap and priority encoder give the same answer in a fixed one or two cycles whether the book has three price levels or three thousand. Trading flexibility for predictability, on purpose, is most of what hardware design is.

04 — IP BLOCKSDo you need to make them? Mostly no

"IP block" means two different things, and conflating them is the usual source of confusion.

The two meanings

SenseWhat it isDo you need it?
a reusable module A module with standard interfaces that does one job and can be dropped into another design. You get this by writing clean SystemVerilog with AXI-Stream ports. Yes — and you already are. Every module in the diagram above qualifies. This is what an interviewer means by "my parser IP".
a Vivado package An .xci with a GUI customisation dialog, draggable into IP Integrator's block design canvas. No. That is packaging, not design. Useful for assembling big systems from many pieces; pointless when building and measuring one datapath.

Why the verification boundary sits where it does. The design is tested at the AXI-Stream port — exactly where a real MAC would hand bytes over. That keeps every interesting part testable with no board and no vendor IP, while the interface stays the real one, so the work would drop straight into a physical design.

Optional polish for the very end: package the top level as IP with ipx::package_project. An afternoon's work, it proves you understand interface inference and AXI conventions, and it reads well in a write-up. Never before the logic is measured.

05 — WORKED EXAMPLEOne cancel message, end to end

An Order Cancel (X) is 23 bytes and contains almost no information. Following one through shows why the design looks the way it does.

  1. 1526 bytes arrive as 191 AXI-Stream beats
    Eight bytes per clock, one beat every cycle. Nothing can be asked to pause.
  2. hdr_parse skips 62 bytes of headers
    14 Ethernet + 20 IPv4 + 8 UDP + 20 MoldUDP64. The IPv4 header length is read from the packet, and a VLAN tag would shift everything by 4 — hard-code the offset and every field downstream lands wrong.
    The MoldUDP64 sequence number goes out as sideband so gaps can be detected: prev_seq + prev_count == this_seq.
  3. msg_frame finds this message starts at byte 3 of a beat
    It reads the 2-byte length (23), then barrel-shifts the message so it begins at bit 0 — pulling the tail out of the next beat, because a 23-byte message starting at offset 3 straddles the boundary. This is the hardest module in the project.
  4. decode slices out the fields, all in one cycle
    58 · 000e · 0000 · 0a4a4c8f2b31 · 000000000004f2a1 · 00000064
    X, locate 14 (AAPL today), tracking 0, timestamp, order reference 324769, 100 shares cancelled. No side. No price. No symbol.
  5. order_table looks up reference 324769 — the unavoidable wait
    Hash it to an address, read the BRAM, compare the stored tag to confirm this entry really is order 324769 and not a collision. The read costs a cycle, so a message arriving right behind this one needs read-during-write forwarding to see the updated value.
    Out comes what the message never said: buy, $153.42.
  6. price_levels subtracts 100 at tick $153.42
    If that level hits zero, its bit clears in the 4096-bit bitmap.
  7. priority_encoder finds the new best bid
    Highest set bit in the bid bitmap, via 64 groups of 64 bits. One to two cycles, the same whether the book has three levels or three thousand — which is the property the whole design exists to have.
  8. BBO out
    Measured from the message's final byte to the updated BBO, this is the latency number that step 10 reports. It replaces "low latency" on a résumé with a figure you can defend.

The whole design in one observation. That cancel message carried an order number and a share count. Everything else the book needed — which side, which price, which symbol — had to come out of a memory holding state from earlier in the day.

That is why there is an order table, why its read latency sits on the critical path of every single message, why a hash collision means silently losing an order, and why model/sizing.py measures the peak number of live orders before a line of that module gets written.
